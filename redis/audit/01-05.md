## Расхождения и конкретные исправления

### C1 — EXISTS показан как будто это внутренняя стадия SET (P2)

Текущее `first-key` шаг2: команда `EXISTS user:1 → (integer)0` при продолжающейся анимации SET. В реальном обработчике это вызов lookupKeyWriteWithDictEntry, не исполнение EXISTS. Предлагается оставить SET в командной строке, а в detail явно сказать RU: «Это внутренний поиск, а не отдельная команда EXISTS от клиента». EN: “This is an internal lookup, not a separate EXISTS command from the client.” Иначе наглядный рассказ начинает показывать другой сетевой обмен.

### C2 — пример ошибки меняет текущую команду между успешным SET и +OK (P2, ясность)

В `request` шаг5 показан `SET user:1` с wrong arity, а шаг6 возвращается к +OK успешной полной команды. Проверка ошибки корректна сама по себе. Уточнение detail RU: «В нашем SET все проверки проходят. Отдельный пример ниже показывает ошибку неполной команды; она не меняет данные». EN: “Our SET passes these checks. The separate example below shows an arity error; that command does not mutate data.” Тип на общей схеме — не универсальный check для SET, поскольку обычный SET перезаписывает любой прежний тип. Уже имеющийся detail правильно говорит «там, где нужен»; в scene лучше `arity · ACL · state` вместо `arity · ACL · type`, чтобы не обещать SET WRONGTYPE.

### C3 — включённые I/O threads и исключения (P2, граница модели)

Существующий detail говорит «могут», что верно. Но основной caption без оговорки создаёт впечатление включённого по умолчанию пула. Добавить RU: «Если включить I/O threads, они помогают с сетью. Обычные команды над ключами по-прежнему идут последовательно». EN: “When enabled, I/O threads help with networking. Ordinary key commands still execute sequentially.” В deeper указать default `io-threads1`; `io-threads4` включает три дополнительных сетевых потока плюс основной. Рисунок с единым event loop — логическая схема; фактическая Redis8 реализация создаёт отдельные ae event loops для I/O workers. Фоновые fsync/lazyfree идут в BIO threads, RDB — отдельный процесс, и специализированные подсистемы не обещают единственный CPU executor.

### C4 — долгий EVAL может вернуть BUSY вместо ожидания окончания (P2)

Текущий caption `event-loop` шаг6: «Даже короткий PING клиента C теперь ждёт её завершения» / “Even C’s short PING must now wait for it to finish.” Это слишком сильная формулировка для Lua произвольной длительности. Предлагаемый caption RU: «Пока исполнитель занят, PING клиента C тоже ждёт. Здесь скрипт завершится до порога ответа BUSY». EN: “While execution is busy, C’s PING waits too. Here, the script finishes before the BUSY threshold.” Detail/deeper должен указать: после `busy-reply-threshold` (default5000ms) Lua не прерывается автоматически; сервер может обработать PING и вернуть BUSY. Обычные команды не начинают изменять общий набор данных внутри Lua. Длительность учебной анимации не измеряет runtime скрипта.

### C5 — обе таблицы и «bounded» rehash (P2)

Текущий dictionary caption шаг6: «Пока он не завершён, Redis ищет ключи в обеих таблицах» / “Until it finishes, Redis checks both tables when looking up a key.” Исправить RU: «Перенос (rehash) идёт порциями. Пока он не завершён, поиск может проверить обе таблицы». EN: “Rehashing moves entries in batches. A lookup may inspect both tables while the move is in progress.” Код возвращает найденную запись сразу; пропускает уже перенесённый старый bucket. Detail “bounded batches” не должен обещать жёстко ограниченное время: одна порция может переносить длинную collision chain, а выделение нового массива тоже требует времени. Новая deeper RU: «Порции уменьшают размер разовой работы, но не гарантируют верхнюю границу задержки: одну длинную цепочку переносят целиком». EN: “Batches reduce the work done at once but do not impose a strict latency bound: one long collision chain moves as a whole.”

### C6 — кнопка Add text допускает неверную интерпретацию APPEND (P2)

В lab String действие `text` выводит `embstr`, оставаясь abstract “Добавить текст”/“Add text”. Если понимать это как APPEND к int42, настоящий Redis возвращает raw даже для43 bytes or fewer. Чтобы модель воспроизводилась, подписать для String действие `SET demo hello`, growth — `SET demo:80 bytes`, и пояснить, что это замена строки командой SET, а не APPEND. Выбор типа Hash/List/Set/ZSet может сохранять add-text label. Общая строка count1 не является точной длиной integer payload и должна называться length/items условно либо явно показывать “пример”.

### C7 — модель List count6000 не определяет encoding без workload (P2)

Текущая модель всегда выводит quicklist при count6000 и обещает «короткие элементы ... около8KiB». В Redis8 проверка перед RPUSH складывает текущие lpBytes и длины новых payload, поэтому один batch6000 односимвольных аргументов может остаться listpack. Native case ниже это воспроизводит. Исправление: зафиксировать в lab рост как один RPUSH6000 двухбайтовых ASCII элементов `aa` (payload12KiB), и в note назвать именно этот выбранный workload. Это даёт quicklist воспроизводимо; не устанавливать универсальную границу в6000 элементов. В detail List дополнить: один очень крупный элемент может храниться отдельным plain node внутри quicklist; при уменьшении списка возможна обратная конверсия quicklist→listpack с hysteresis.

### C8 — конверсия Set визуально заменяет членов (P2)

Desktop `encodings(s===2)` показывает intset `[2,5,8,13]` → hashtable `apple/orange`, compact аналогично `[2,5,8,13]` → `apple`. Ни размер, ни конверсия не меняют members. Нужно сохранить числа в обеих схемах: hashtable `2→∅`, `5→∅`, `8→∅`, `13→∅` (можно компактно две строки), а слово “growth” пометить `…more members` или показать одного нового члена дополнительно. Связанные motion attrs/roles не менять.

### C9 — пропущен Hash listpackex (P2)

В deeper полный список сейчас “Hash listpack/hashtable”. Код8.0.0 при первом field TTL конвертирует listpack→LISTPACK_EX и OBJECT ENCODING выдаёт `listpackex`; публичная latest OBJECT ENCODING страница сама не перечисляет этот вариант. Здесь исходник точнее обзора документации. Сохранить основной шаг про Hash без field TTL, а detail/deeper добавить RU: «В этой сцене у полей нет TTL. Небольшой Hash с TTL отдельных полей может использовать listpackex: к парам поле/значение добавляется метаинформация срока». EN: “Fields have no TTL in this scene. A small Hash with field expiration can use listpackex, which adds expiry metadata to field/value pairs.” Явно ограничить lab Hash режимом without field TTL, а полный список исправить на listpack/listpackex/hashtable.

### C10 — порядок Sorted Set при одинаковом score (P3, полезная полнота)

Фраза «порядок по score» верна, но не полна. В detail добавить RU «При равном score порядок задаёт бинарное сравнение имён участников». EN: “Members with equal scores are ordered by their binary lexical value.” Не менять главную простую подпись.

## Отдельные замечания по deeper, моделям и сценам

- `first-key` deeper о binary-safe strings верен. Отдельного объекта ключа robj в постоянном db dict здесь не обещается: фактический dbAddInternal сохраняет SDS key, robj value. GET не меняет само значение, хотя может менять LRU/LFU и удалять логически просроченный ключ; lab в первой главе без TTL корректен.
- `request` deeper RESP2/RESP3, nil display, byte lengths, AUTH/HELLO/ACL/TLS верны в заявленном объёме. Model parser не настоящий RESP decoder: он сравнивает собранную строку с единственным фиксированным wire. В lab это допустимо, так как scope явно учебный. Полностью ошибочный RESP в Redis может приводить к закрытию соединения, тогда как обычная arity error не закрывает его; lab не моделирует error bytes.
- `event-loop` lab восьмитактовый KEYS на одной counter — абстракция стоимости, не benchmark. `cost8` не является реальным числом scheduler ticks. Уже есть “учебных тактов”; следует сохранить. Можно дополнить lab note: «Порядок очереди выбран сценарием». I/O action только готовит байты, не исполняет command — соответствует source.
- `dictionary` lab честно указывает byte-sum вместо SipHash; фиксированные ASCII keys делают его формулировку корректной. При rehash old table сейчас живёт до cursor==capacity, даже если последний ключ перенесён раньше. Реальный dictCheckRehashingCompleted освобождает old table при ht_used[0]==0. Исправить завершение после переноса последнего оставшегося ключа; при пустой old таблице её следует сразу отпустить. Это улучшает именно lifecycle, не требует имитировать все heuristics Redis.
- `dictionary` static scenes корректно показывают две таблицы в переходный момент; значения bucket2/user:1 и bucket6 не являются фиксированным SipHash результатом. Добавить к deeper, что hash seed и размеры на рисунке условны. В standalone Redis8 kvstore содержит один lazy-allocated dict; в Cluster — per-slot dictionaries; это не нужно сворачивать в утверждение о единственной таблице во всех режимах.
- `encodings` lab допустимо показывает только несколько выбранных состояний, а не все conversion paths. Точные пороги при дефолтах: intset512; set listpack128/maxmember64B; Hash listpack512/maxfieldorvalue64B; ZSet listpack128/maxmember64B; list fill-2 задаёт целевой8KiB размер. Counts513/129 действительно переводят тестовые небольшие values в general encoding, но oversized member может сделать это раньше, а size hints/operation history имеют значение.
- `choreography` первых30 шагов задаёт teaching time; header прямо отвергает трактовку как performance measurements. Причинный порядок request→mutation→reply корректен. Step first-key1–4 — продолжение одной логической SET, хотя отдельные intermediate scenes повторно рисуют request arrow; это не должно означать повторное исполнение SET. `request` flow arrow output→client в компактной сцене пространственно не возвращается к TCP, это схематическая logical flow, а не фактический network topology. Не найдено утверждений о disk/replica ACK до локальной мутации в этих пяти главах.
